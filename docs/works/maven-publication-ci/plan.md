## Implementation strategy and ownership

Use the small project-local `gradle/maven-publication-ci.gradle.kts`, now applied from the root build, for typed publication inspection, a named repository `ciMaven`, and root aggregate `publishCiMaven`. Its retained generation-2 code/effects are recorded in Context; writing candidate-policy code early does not prove S2. This is ordinary build wiring for this project, not a reusable publishing framework. Proposed `.github/scripts/publish_maven.ts` runs under the repository-pinned Deno runtime and uses TypeScript with Deno's built-in filesystem, subprocess and path APIs for workflow orchestration and Git operations; focused tests/fixtures live alongside it. No external publisher or npm package is required. The Deno driver/tests remain proposed future write locations, not existing implementation evidence; the Gradle script and local consumer/producer fixtures already exist.

Attach `ciMaven` to each project with `maven-publish`, including the root if it acquires publications. Build the inventory from all final `MavenPublication` containers and associate each with its `PublishToMavenRepository` task for `ciMaven`, including late plugin markers. Do not derive coordinates from directory names or version properties, hard-code publication counts, or publish the undirected `publish` aggregate. Reject an empty overall set, unsafe coordinate-derived paths, duplicate version destinations, missing task coverage or missing configured outputs before accepting a candidate. Projects with no publications contribute none.

Use the checked-in Gradle 9.8.2 wrapper, the user-selected baseline. The configuration validation observed Kotlin 2.4.10, KSP 2.3.12 and JetBrains JBR 21.0.11, reusing the user's existing Gradle home and proxy; do not alter global properties. `help` and `javaToolchains` both exited 0, and JDK 8, 11, 16, 17, 21 and 25 were discovered. This is configuration evidence only. A later actual complete publication succeeded on Microsoft JDK 17, not the required runtime JDK 21; JDK 8 `tools.jar` and actual JDK 8/11 toolchain correlation remain incomplete. Preserve the runtime JDK 21 producer/consumer acceptance requirement and original targets. Do not combine old JDK 21 configuration with JDK 17 publication as if they prove one accepted JDK 21 producer. Use `--no-configure-on-demand --no-configuration-cache --no-parallel`, so every project's publishing configuration is visible and the dedicated tree has one controlled writer. Start with task-graph/configuration inspection before the full publication run; failure to configure an included IntelliJ project is a blocking implementation finding, not permission to exclude it or alter dependency policy.

Use two independent temporary directories outside the source checkout and caches: an immutable destination-baseline export and a candidate filesystem repository. The Deno/TypeScript driver fetches the current `maven` head once it holds the workflow writer slot, exports only its tree, and seeds the candidate; absent branch means empty directories. Pass their paths as Gradle properties, with path separation checked before deletion or publication. The driver may use Deno built-in `Deno.Command`, `Deno.readDir`/`Deno.readFile`, `Deno.writeFile`, `Deno.mkdir` and `Deno.remove` APIs; it requires only `--allow-read`, `--allow-write`, `--allow-run=git,./gradlew` and the narrowly required `--allow-env` variables. Do not use `mavenLocal`, the central repository or `markerTest` as seeds. Keep temporary files and Git internals outside the published tree.

Within the Gradle task path, inventory first, then prepare current release-version directories before any destination publishing task runs: remove those directories from the candidate only, retaining the immutable baseline and artifact-level metadata. This makes every current release-version path set freshly generated; obsolete seeded files cannot mask removed outputs. Keep snapshot directories intact for native timestamp/history generation. Wire preparation before every selected destination task and final validation after all of them. Retain dependency build outputs and Gradle-generated sidecars; never synthesize Maven XML or checksums.

For each release identity compare the regenerated directory's complete relative-path set and bytes to its baseline directory. Absent baseline accepts a complete new payload; equality retains/restores the baseline payload; any differing/added/removed file rejects the entire candidate and names the identity and required version bump. An existing incomplete baseline conflicts. Artifact-level metadata and its checksums remain the native generated result; version-directory files have no normalization exception. Verify configured artifacts, POM identities, applicable `.module` files, checksum integrity and marker implementation dependencies. Keep snapshot history and unrelated coordinates byte-for-byte except where native publication legitimately updates their own metadata. Discard any failed candidate; no Git update follows a generation or validation failure.

Repeat actual producer publication with forced artifact regeneration into independent candidates, not just reuse of an existing output or build cache. If archive timestamps/order prevent repeatability, make the minimum affected archive-task reproducibility adjustment, preserving artifact content and coordinates. Do not relax payload equality, normalize published bytes or exclude checksums. Other repeatability/configuration failures must be reported with the blocking source and evidence; broad dependency changes or authority changes require separate reconciliation.

The workflow uses `push` on `main` with `**/gradle.properties`, plus `workflow_dispatch`, `contents: write`, and a fixed repository Maven concurrency group with `cancel-in-progress: false`. Reject non-`refs/heads/main` events before publication. Check out the immutable event SHA, including on reruns; never substitute the latest main checkout. Keep existing HTTP definitions intact and prove none of their tasks or Marketplace/test publication tasks enter this graph. No HTTP/Marketplace credentials are needed.

The Deno/TypeScript driver stages the checked candidate in an isolated Git checkout parented by the fetched destination head; for an absent branch, initialize an independent orphan history with only Maven files. Immediately before a destination update, read remote `refs/heads/main`; mismatch returns a distinct skipped outcome and lookup failure fails closed. Use a non-force push of the one complete candidate commit to `refs/heads/maven`. A concurrent destination advance rejects the attempt; no generic retry or force push. An ambiguous push outcome requires checking the remote head against the expected commit before claiming success. A byte-identical candidate avoids an empty commit, after eligibility/freshness checks. Logs distinguish success/no-change, ineligible/stale skip, and failure. Authentication uses the same repository's token without putting secrets in logs, URLs or artifacts.

## Risks, compatibility and recovery

The original Gradle settings/configuration failure was resolved for configuration with the user-selected Gradle/KSP/JDK baseline. Later generation 2 separately established a complete empty-baseline publication on Microsoft 17, but not the required JDK 21/toolchain-correlated S1 acceptance, byte reproducibility, Java 11 variant consumption or safe Git updates. These remain explicit acceptance work, not reopened publishing policies. Never bypass a failing publication by dropping it. Isolate tests from global caches, real destinations and current user files. Do not serialize independent repository workflows together; this repository's fixed concurrency key is sufficient, with non-force Git push protecting against external writers. GitHub's pending-run ordering is not a publication ordering guarantee; the main-HEAD checkpoint remains necessary.

Before the final push, recovery is to discard only the temporary candidate and return failure or skip; the baseline and destination remain intact. After a destination advance, a later attempt must fetch and regenerate from that newer baseline and recheck source freshness. There is no automatic rollback, force restoration, retention cleanup or source-tag manipulation. Existing HTTP publishing remains separately available. Hosted CI, token authorization, branch protection and actual remote storage behavior require a later authorized run and cannot be certified by local fixtures.

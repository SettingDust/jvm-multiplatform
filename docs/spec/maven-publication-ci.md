# Maven publication CI

Status: Ready for implementation at the contract level. The user-confirmed release, snapshot, and source-eligibility policies are incorporated below. This Spec defines the publishing contract and required checks; it does not establish that CI exists or that publishing has succeeded.

Authority: [Git-backed Maven publishing ADR](../adr/git-backed-maven-publishing.md). No PRD change is required for this infrastructure work. The current local working tree is the preparation baseline. Existing module Specs and Plans retain their own scope; this document does not extend them.

## Boundary and triggers

- CI must publish a Maven repository to the root of the `maven` branch in `github.repository`, using that repository's `GITHUB_TOKEN` with `contents: write`.
- Automatic publication must run only for `push` events to `main` matching `**/gradle.properties`, including the root `gradle.properties`. CI must also expose `workflow_dispatch`.
- Pull requests, pushes to other source branches, and tags must not automatically publish. A push to `main` without a matching path must not automatically publish. Workflow-file changes alone therefore require manual execution if publication is desired.
- Both automatic and manual publication must use `refs/heads/main`. An automatic run must build its triggering source commit; a manual run must build the event's source commit for the selected `main` ref. A dispatch selecting another branch or a tag is ineligible and must not publish. A rerun must retain its original source commit rather than silently build a newer commit.
- Immediately before updating the destination branch, CI must read the current remote `main` HEAD and compare it with the built source commit. If they differ, the run is stale and must skip publication without changing the destination. A rerun whose source commit is still the current `main` HEAD is eligible. Failure to establish the current HEAD must prevent publication. This check concerns source freshness at that checkpoint; it does not atomically lock `main` or guarantee increasing Maven version numbers.
- Publication must not create, move, or delete source tags or write to the source branch. The central Maven repository and former `maven-repo` branches are outside this CI's destination.
- The new CI path must not invoke existing HTTP publishing destinations or require their credentials. Their existing Gradle configuration and usability must be preserved. IntelliJ Marketplace publishing is also outside this Maven CI.

Gradle plugin markers use group `<plugin-id>` and artifact `<plugin-id>.gradle.plugin`, with a POM dependency on their implementation publication. Consequently, copying only a presumed implementation-group directory is insufficient. A marker may contain only a POM; CI must not require a marker JAR. Configured source artifacts and Gradle Module Metadata, including the Java 11 feature, must not be lost by copying only primary JARs and POMs.

The `classpath-api-stubs` `markerTest` repository is a test destination for existing publications, not a separate publication set or the CI output. Its randomized output directory must not be copied as the Maven branch.

## Native Gradle output and metadata

1. CI must use the checked-in wrapper, currently [Gradle 9.2.0](../../gradle/wrapper/gradle-wrapper.properties), and an explicitly named `publishing.repositories.maven` repository whose URL is a dedicated local filesystem directory. That directory must be separate from source files, `mavenLocal`, and test repositories. Its exact name and location are implementation details.
2. CI must select the tasks publishing all configured Maven publications to that named repository, including publications added by plugins after evaluation. Gradle's `publish<Publication>PublicationTo<Repository>Repository` tasks or the corresponding destination-specific aggregate are suitable. The undirected `publish` aggregate must not be used: it also targets configured HTTP and test repositories. Redirecting `publishToMavenLocal` is not equivalent to publishing to a named filesystem Maven repository.
3. For a new `maven` branch the output starts empty. For an existing branch, CI must seed the dedicated directory from that branch's Maven tree, excluding Git internals, before Gradle publishes into it. Existing versions and unrelated coordinates already on that branch must survive. CI must not seed from the central repository or a developer's local Maven cache. There is no migration or pruning in this contract.
4. Gradle must generate the POMs, configured artifacts, applicable `.module` files, repository metadata, and checksum sidecars through its normal Maven repository publisher. CI must retain the generated files, with normal Maven paths at the branch root; it must not wrap them in an extra output-directory level or rewrite coordinates and XML itself. The candidate must satisfy the version-payload policy below before it can update the destination.
5. Existing artifact-level `maven-metadata.xml` must be available to Gradle during publication. Gradle 9.2.0 reads its version list, adds the published version if absent, sets `latest` to the version just published and `release` to it for a non-snapshot, and updates the timestamp. These fields are not a semantic-version maximum. CI must use these native semantics without a custom metadata merger. A fresh-output-only overlay onto an existing branch would lose historical version-list entries and does not satisfy this contract.
6. The named filesystem repository uses repository metadata (`maven-metadata.xml`) and repository checksum generation. `maven-metadata-local.xml` from `mavenLocal` is not a substitute. For snapshot versions, Gradle's repository publisher supplies the timestamped snapshot artifacts and metadata; CI must not rename them by hand. It must retain historical snapshots as specified below.

These metadata details resolve the ADR's former implementation question using the wrapper-matched [Maven Publish documentation](https://docs.gradle.org/9.2.0/userguide/publishing_maven.html), [Java Gradle Plugin publication documentation](https://docs.gradle.org/9.2.0/userguide/java_gradle_plugin.html#maven_publish_plugin), and Gradle 9.2.0 source: [AbstractMavenPublisher](https://github.com/gradle/gradle/blob/v9.2.0/platforms/software/maven/src/main/java/org/gradle/api/publish/maven/internal/publisher/AbstractMavenPublisher.java), [MavenRemotePublisher](https://github.com/gradle/gradle/blob/v9.2.0/platforms/software/maven/src/main/java/org/gradle/api/publish/maven/internal/publisher/MavenRemotePublisher.java), and [MavenLocalPublisher](https://github.com/gradle/gradle/blob/v9.2.0/platforms/software/maven/src/main/java/org/gradle/api/publish/maven/internal/publisher/MavenLocalPublisher.java). They are source-backed behavior, not an executed publication check.

## Version payload and repeat publication

The version identity is Gradle's `(groupId, artifactId, version)`, including each plugin marker's own identity. The version payload is the complete relative-path set and file bytes beneath that identity's Maven version directory. It includes POMs, `.module` files, every configured artifact and classifier, and all generated checksum sidecars. A POM-only marker is a complete payload when that is everything Gradle publishes for it.

- For a release version with no existing payload, CI must add the complete generated payload.
- For an existing release version, CI must compare the complete newly generated payload with the destination baseline. Equality requires identical relative-path sets and byte-identical files. An identical complete version must be skipped and its existing payload retained; this permits a one-module version bump to process unchanged publications in the complete publication set.
- Any differing, added, or removed release-version file is a conflict. CI must fail the publication attempt, leave the entire destination unchanged, and report the affected identity and the need for a version bump. This includes an incomplete existing payload and differences in POMs, `.module` files, classifiers, or checksums. No release-version file may be silently excluded, normalized, or overwritten to make the comparison pass.
- The comparison must distinguish files actually generated for the current publication from files inherited by seeding. A seeded obsolete file cannot disguise a removed output. The implementation may choose how to obtain the complete generated path set; this contract requires no manifest or receipt framework.
- Artifact-level repository metadata at `<group-path>/<artifactId>/maven-metadata.xml` and its checksum sidecars sit outside the version payload. Gradle may update them using its native semantics, including timestamps and `latest`/`release`. This exception does not exclude any file inside a release version directory. Skipping an identical release payload does not require skipping candidate generation or suppressing native repository metadata updates.
- Snapshot versions may be updated by Gradle's native repository publisher, including version-level snapshot metadata and its checksum sidecars. Previously published timestamped snapshots and other historical versions must remain in the seeded tree. CI must add no snapshot cleanup, retention limit, or pruning mechanism.

All required publications must pass these checks before any branch update. A conflict in one version must prevent exposing other newly generated versions from that attempt. Source eligibility is independent of version ordering: the current `main` commit may configure an older version, and its publication remains subject to the same payload rules and Gradle's last-published metadata semantics.

## Completion and failure

- CI must expose a candidate Maven tree only after every required publication task and the relevant output checks succeed. A failed, empty, incomplete, invalid, cancelled, or timed-out generation must leave the destination branch unchanged and must not be reported as successful publication. A project with no publications is valid; an empty overall publication set is not. An ineligible ref or stale source must be reported as skipped without a publication update.
- CI must serialize writes to this repository's Maven destination without cancelling an active writer. It must base the candidate on the current destination head and use a non-force push. If the destination advances before the push, that attempt must fail without overwriting the newer head; any subsequent attempt must start from the newer baseline and recheck source freshness. Generic retries or a custom transaction protocol are not required.
- The destination update must contain the complete checked candidate in one branch update, retaining previous repository content. If the branch is absent, CI must create it with only the Maven tree. A permission or push failure must be surfaced as failure. If a push outcome is uncertain, CI must not assert success without confirming the destination update.
- After version-payload checks and source eligibility succeed, a byte-identical candidate may finish successfully without creating an empty commit. Identical release payloads do not imply an identical candidate tree: Gradle may have updated repository metadata and its checksums.

## Acceptance conditions

These are required future checks, not checks executed while writing this document. A small publication fixture and focused workflow/task inspection are sufficient; no cross-platform matrix, shared publisher, manifest, receipt, or audit framework is required.

| Check | Observable acceptance condition |
| --- | --- |
| Trigger and permission inspection | Workflow has `push` on `main` with `**/gradle.properties`, manual dispatch, and the required token permission. Root and nested property changes match; unrelated changes, PRs, other-branch pushes and tags do not automatically publish. Manual selection of a non-`main` ref produces no destination update. |
| Source freshness and reruns | In a bounded fixture, check matching source and remote `main` HEAD, a stale source, a `main` advance during generation, and failure to read `main` HEAD. Check immediately before the destination update; stale cases are skipped and lookup failure prevents publication. A rerun of the still-current source commit is eligible, while a rerun of an older source is skipped without substituting a newer checkout. |
| Configured publication/task inspection | After configuration, compare the actual `MavenPublication` containers with the tasks targeting the dedicated local repository. Every publication is covered, including all plugin markers; projects with no publications add none. The CI task graph has no HTTP or Marketplace publish tasks and does not need their credentials. Do not assert a fixed publication or file count. |
| Local Maven output | Generate the complete set into the dedicated directory. Check Maven paths and POM identities against Gradle publication identities; retain all configured artifacts, `.module` files and generated checksums. Check each marker POM's implementation dependency. Resolve at least one plugin by its ID from this repository with a fresh consumer cache and resolve `java-processor-util`'s Java 11 variant from its metadata. Existing marker-test evidence alone does not prove the new CI destination works. |
| Existing repository metadata | In a bounded local fixture, seed an older release and an unrelated coordinate, publish a different version through the named filesystem repository, and check both versions remain listed, prior content survives, and metadata/checksums match Gradle's output. Publishing a new older-numbered version from an eligible current source must retain native last-published `latest`/`release` behavior; current `main` is not a version-ordering guarantee. |
| Release repeat and conflict | Check a new release, an identical complete existing release, and changed, added, or removed files in an existing release. Cover POM-only markers, `.module` files, classifiers, checksum differences, and a seeded obsolete file masking a removed output. Identical versions retain their payload; any conflict fails the entire update and reports the identity and required version bump. Demonstrate a one-module bump alongside unchanged modules. Repository metadata changes alone must not be mistaken for release-payload conflicts. |
| Snapshot repeat | Publish the same snapshot version twice through the named filesystem repository using distinct native snapshot timestamps. Check native snapshot metadata and checksum updates, resolution of the current snapshot, and retention of the earlier timestamped artifacts and unrelated historical content. No cleanup mechanism is required. |
| Branch update and failure | Against a disposable local Git destination, check absent-branch initialization, an existing-branch update, generation failure, and a stale-head non-force push rejection. Successful updates expose the complete Maven tree at root and preserve history/content; failures expose no partial tree. Verify that source refs/tags are not modified. Live token permissions and remote publication require a later authorized CI run. |

## Document self-check

The earlier draft's source inspection covered the root settings/build, every included project's available build script, version properties, wrapper version, and the accepted ADR. Its expected publication table and relative links were checked against local files. Gradle's wrapper-matched documentation and publisher source were inspected to distinguish named filesystem repository publishing from `mavenLocal` and to establish metadata history behavior.

This revision incorporates the user's confirmed policies and checks them against the accepted ADR: identical complete releases are skipped, any release-payload difference fails and requires a version bump, snapshots use native updates while retaining history, and both trigger paths require `main` with a current-HEAD check before publication. The two original unresolved policy items are closed. The full-payload and mutable-metadata boundaries, seeded-output comparison requirement, and acceptance cases make those rules verifiable without prescribing a comparison framework.

The ADR's obsolete follow-up wording is synchronized with this Spec. At the document level there is no remaining authority or policy blocker. Implementation details and the required future acceptance checks above remain unverified.

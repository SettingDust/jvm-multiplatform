## Scope and invariants

- Add a boolean `preserveMethodBodies` task input with default `false`. One input keeps existing passthrough (with Code) for either value. Multiple inputs with the switch off keep the bodyless intersection. With it on, only declarations surviving existing class/member/signature/access intersection may retain Code, and only if every contributing original method has comparable, equal Code.
- Compare the full ordered sequence of executable instructions (including unreachable instructions), typed operands and constants by value/kind (nested `ConstantDynamic` and `invokedynamic` arguments included), branch/switch targets mapped to executable positions including a distinct end sentinel, and the full ordered handler table with end-exclusive boundaries, handler targets, and caught types. Unsupported instruction or constant kinds are uncomparable, not equal.
- Ignore line numbers, local-variable debug data, redundant/debug/frame-only labels, frame encoding/contents, and source `max_stack`/`max_locals` when deciding equality. Compare all Code type annotations by target position and value (including instruction, handler, and local-variable targets), or conservatively mark the affected Code uncomparable. Any other Code metadata whose equality cannot be established reliably also prevents preservation. Distinguish absent Code from Code with no executable instructions; abstract/native have no Code.
- On match, carry complete Code from one original method as a coherent unit, including its own instructions, labels, handlers, annotations, frames, debug data, and maxima, while keeping the intersected declaration and method-level annotations/exceptions as owned by the existing intersector. On mismatch, missing Code, or uncertainty, emit the already-common declaration without Code, without synthesizing Code or failing solely for the difference. `<init>` and `<clinit>` use the same rule. The retain/omit decision must be symmetric and order-independent for two or more inputs; output bytes and selected debug data need not be.
- Do not change class/member selection, method signature or access policy, excluded-artifact selection/copy semantics, or infer consistency of referenced helpers. No worker/coroutine, Cloche/Codev, publishing/rollout, or historical refactoring work.

## Strategy and ownership

1. In `GenerateStubApi`, expose the option and propagate it through `StubGenerator` into body-selection logic. Keep the one-input path unmodified in effect. Replace the insufficient `@CompileClasspath` file normalization for body-bearing included inputs and copied excluded files with tracking that observes changes to their bytes even for single-input passthrough with the switch off. Keep the option an `@Input`. Evaluate Gradle up-to-date and build-cache behavior in the task fixture, not only the annotation change.
2. In `StubGenerator`, preserve the existing reduction for declarations and resolve candidates against the original nodes from every input after intersection. Do not compare intermediate bodyless `MethodNode`s or let a mismatched early pair become an apparently valid later match. Feed qualifying Code into an already-intersected method declaration without replacing its method-level intersection. Treat a `Code` presence marker separately from instruction count if the ASM tree representation alone cannot distinguish them.
3. Keep the body comparison local to `classpath-api-stubs`, using its existing ASM dependency. Normalize label references to instruction-position indexes plus an end sentinel; cover operand kinds, literal values, bootstrap data, ordered handlers, and Code annotation targets. Use conservative uncomparable handling for unsupported metadata or values. Copy a whole chosen source Code section rather than mixing Code components from inputs; do not introduce a bytecode verifier or dependency-closure search.
4. Add focused ASM-generated class/jar fixtures and ASM-reading assertions of emitted `Code`/declarations. Exercise the task with Gradle TestKit or an equivalent real Gradle task fixture that can be registered against this checkout (the declared plugin implementation class is absent at the inspected baseline). Keep fixtures small and scoped to the behavior below.

- ASM-read generated jars for one input with either switch value, multiple inputs disabled, two and three matching bodies enabled, reversed input order, and common declarations without Code when one body differs, is missing, or is uncomparable. A bytecode body referencing an absent or different helper remains a shape-only result, not a reason to assert executability.
- Fixture variations must exercise opcode/operand, switch and jump destination, nested constant/bootstrap argument, and handler range/type/order changes as negative cases; source line, redundant labels, local-variable debug information, and frame representation changes as positive cases. Include Code annotations either with position/value comparison or conservative omission, and unsupported Code metadata as an omission case. Ensure the absence-of-Code distinction is tested independently of zero executable instructions where representable.
- Run the appropriate package tests in the implementation worktree (for example `./gradlew :classpath-api-stubs:test` when the checkout/toolchain allows). For a Gradle task fixture, change only an included input jar's method body without ABI change and observe reevaluation and the selected output transition, both with up-to-date checks and with build cache. Repeat single-input body-only change with the switch on and off; toggle the switch and observe a changed task input state. Change an excluded copied artifact and verify its changed bytes cannot yield a stale copied output. A cache hit is acceptable only when computed for matching input bytes and option.
- Completion gate: checks above pass, final source diff remains limited to `classpath-api-stubs` and matches the Spec, and test evidence distinguishes the behavior actually observed from any environment limitation. Do not make stub compilation, JVM load/execution, frame verification, or cross-version injection a gate.

## Risks and limits

ASM presents Code data across instructions, handlers, annotations, and attributes; an opcode-only or tree-node identity comparison is unsound. If an attribute cannot confidently be classified/compared as Code metadata, omit that candidate's Code. Cloning the entire `MethodNode` could overwrite existing declaration metadata; verify emitted intersection independently. `@CompileClasspath` currently ignores precisely the input differences that matter; both single-input passthrough and excluded copies must be included when assessing normalization. Existing unrelated baseline/plugin wiring failures should be recorded, not disguised as feature failures or repaired out of scope. No migration or rollback mechanism is required for an opt-in task input defaulting to off; disabling it restores multi-input bodyless behavior.

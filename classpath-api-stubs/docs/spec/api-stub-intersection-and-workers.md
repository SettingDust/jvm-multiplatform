# Classpath API Stub Intersection and Worker Execution

Status: Implementation contract for this bounded change. The rules below are the recommended implementation choices authorized for this work, not a claim that each rule received separate user confirmation or that the changes are already implemented.

## Boundary and existing authority

This Spec owns classpath API intersection metadata, inheritance evidence, and task execution in `classpath-api-stubs`. Inputs are ordered classpaths of included and excluded artifacts; the task emits an API jar and copies selected excluded artifacts. Only common, demonstrable API relationships may be emitted. No runtime-equivalence guarantee is implied. The existing [preserve-method-bodies Spec](preserve-method-bodies.md) remains authoritative for Code, default-off behavior, single-input passthrough, all-input body comparison, and byte-sensitive task inputs. If a change to reduction or output threatens that contract, its Code behavior must remain unchanged after integration. No PRD or ADR for these improvements was found in this module.

## Inheritance and generic signatures

- For two or more inputs, the emitted superclass must be a demonstrably common ancestor of every contributing class under its own input classpath, not just an ancestor of a pairwise intermediate node. Use complete internal class/interface names as identities. Pairwise reduction order must not manufacture a common ancestor; two- and three-input permutations must make the same retain/fallback decisions. If parent class bytes are absent, `java/lang/Object` is an allowed conservative fallback, not proof of a more specific ancestor. A corrupt class, I/O error, or detected inheritance cycle must fail generation rather than silently become Object. Resource ownership must cover these failures.
- Emitted raw `superName`, raw `interfaces`, and class `Signature` must agree. Match superinterfaces by complete internal name, independent of input ordering, and preserve generic type arguments only for interfaces present by name in every input. Do not pair unrelated interfaces by list position. No generic claim may contradict the emitted raw header or depend on an unproved ancestor. A raw common interface without provable common generic arguments may remain raw, but an unreliable generic relationship must not survive in `Signature`.
- Class, field, and method signatures must describe only relations supported by all contributing inputs, be syntactically valid, and have erasures compatible with emitted raw superclass/interfaces or JVM field/method descriptors, respectively. For differing bounds, variance, formal parameter counts or identities, thrown types, or type arguments, retain only what can be proved common; otherwise omit the **whole affected Signature attribute** rather than carry one side's claim. A type variable reference must resolve to a compatible formal variable on the emitted class or method (or an applicable enclosing declaration); otherwise omit that Signature. If a class Signature is omitted, re-check field and method Signatures for dangling class type variables and omit the affected attributes. Do not invent generic relationships merely to avoid omission. Omission must leave valid raw descriptors and a stub accepted by representative Java and Kotlin consumers for the supported fixtures.
- One-input output must remain passthrough for class bytes, including Code and metadata. No generic requirement in this section should rewrite that path.

## Method parameter metadata

For common methods identified by JVM name and descriptor, descriptor parameter positions are the alignment authority; compute local-variable slot offsets correctly for static/instance receivers and category-2 parameters. Do not infer names from LocalVariableTable. For multiple inputs:

- Preserve `visibleParameterAnnotations` and `invisibleParameterAnnotations` per corresponding descriptor position only if the annotation table's mapping to descriptor positions is determined for **every** input. Respect each visibility's annotable-parameter count, omitted synthetic/mandated leading positions and applicable `MethodParameters` flags. If layout is ambiguous, omit that visibility's parameter annotations for the affected method rather than shift annotations to another parameter. Compare annotation descriptor and complete values recursively (including nested annotations, enum values, arrays, and primitive/string values); retain only annotations with identical visibility and values on the same parameter across all inputs. Incomplete or conflicting annotation values do not establish equality. The emitted annotable count and arrays must describe exactly the retained, unambiguous positions. A zero-annotation slot is not license to shift later metadata.
- Preserve a `MethodParameters` name at a descriptor position only when all inputs provide the same name at that position and mapping is unambiguous. Do not substitute first-input names or LVT guesses. Emit parameter flags only when they agree for that position across all inputs; if the metadata cannot be represented without implying an unsupported mapping, omit `MethodParameters` for that method. Method descriptors and member selection remain unchanged. Multi-input ordering must not affect retention decisions; a single input still passes through unchanged.

## Worker and resource contract

- `GenerateStubApi` must submit one `noIsolation` Gradle `WorkAction` per task; one action processes that task's entries sequentially. Distinct ready stub tasks may overlap subject to Gradle's worker budget (`--max-workers`); do not set a default global limit of one, add a coroutine dependency, create per-class work submissions, or implement weighted scheduling. Use Gradle's worker quota as the initial limit. A configurable BuildService cap may be considered only on evidence that task overlap exceeds an acceptable memory boundary; it is not part of this change.
- Reduce long-lived retention of complete parsed `ClassNode`s; ancestor queries should use lightweight header information and only cache what is required. Preserve classpath precedence, selected excluded artifacts, body selection, and API contents. Output must be a single-writer streamed jar with an intact manifest and expected entries; output equivalence is semantic (ASM-read class/member/metadata and copied artifact bytes), not byte-for-byte ZIP timestamp equality.
- All input streams, classloaders, and jar writers must close on success and failure, including malformed class, missing entry, I/O, and output exceptions. A partial output must not be mistaken for a successful task artifact; the task must fail on genuine input/output errors. No suppression of the inheritance failure rule above.
- Retain `preserveMethodBodies=false` by default, single-input passthrough, all-input Code consistency when enabled, and full-byte Gradle input tracking for body-bearing or copied inputs as specified by [preserve-method-bodies](preserve-method-bodies.md). Unchanged-input up-to-date and correctly keyed cache reuse remain valid.

## Acceptance evidence

1. Generate two- and three-input fixtures (and permutations) with disordered interfaces, generic superclass/interface/field/method signatures, renamed or conflicting type variables, incompatible bounds and missing generic evidence. Inspect raw headers and every surviving Signature with ASM; compile representative Java and Kotlin consumers against the generated jar, including the no-Signature fallback and formerly dangling type-variable cases. Check a parent chain present in only some inputs falls back to Object; malformed class, parent I/O failure, and cycles fail.
2. Exercise instance/static descriptors with wide parameters, synthetic/mandated prefixes, short annotation tables, both visibilities, matching/conflicting/nested annotation values, and two-/three-input permutations. ASM-read annotation arrays, annotable counts, flags and consensus names; confirm ambiguous layouts omit metadata rather than shift it. LVT differences alone must not supply names.
3. With at least two independent stub tasks and Gradle `--max-workers=2`, observe overlap of worker actions and equivalent outputs; compare representative task outputs (including manifest, excluded copies and Code cases) before/after the worker change. Exercise malformed input and output failure, then verify stream/classloader/jar handles can be released and the task can rerun. Use bounded representative elapsed-time and peak-memory observations with recorded workload, runtime, and worker limit; no unmeasured speedup or OOM-pressure claim.
4. After integration, rerun existing Code preservation tests and a real Gradle task/cache fixture, plus inheritance, parameter, and worker tests. In particular verify default-off multi-input no Code, one-input Code with either setting, three-input matching/mismatching Code, body-only input changes and excluded-copy changes invalidating stale outputs. Root-build failure may be isolated with the reproducible module settings route in the [Plan](../works/api-stub-parallel-improvements/plan.md); it is not evidence that a changed contract passed.

## Exclusions

No changes to actual-stubs, Cloche, Codev, release/publishing, runtime semantics, weighted scheduling, OOM stress tests, or historical completed records. Verification of Java/Kotlin consumers is confined to the targeted inheritance/generic fixtures, not a promise that every generated jar can execute or verify.

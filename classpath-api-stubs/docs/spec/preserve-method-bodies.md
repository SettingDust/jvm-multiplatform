# Preserve Method Bodies in Classpath API Stubs

Status: **Behavior confirmed; implementation pending**. This is the owning technical Spec for `classpath-api-stubs`. The requirements below record the accepted behavior, not an approved implementation Plan or a claim that the feature is implemented. It does not instruct a Cloche change or restore the historical implementation.

## Boundary and accepted intent

- `GenerateStubApi` produces a common classpath stub from input classpaths through `StubGenerator` and `ClassNodeIntersector`. The feature concerns the `Code` of methods already selected by that intersection, not a new policy for selecting classes, signatures, fields, or methods.
- The stubs are for bytecode-reading tools such as Mixin, to make those tools easier to author against a common view. A retained method body is evidence of a shared bytecode shape, **not** an executable implementation.
- For multiple inputs, preservation must be limited to method bodies that are consistent across **all** contributing inputs. An identical-looking call site must not be taken to prove that its referenced helper exists in the stub, has the same implementation on each platform, or has the same runtime meaning.
- Successful compilation, JVM loading or execution, frame verification, dependency closure, and successful cross-version injection are **not** guarantees. This does not waive the need to emit a bytecode artifact that the intended analysis tool can read.
- Historical `preserveMethodBodies` code is reference material, not authority for behavior or implementation details.

The present implementation has no `preserveMethodBodies` switch: multi-input intersection constructs new `MethodNode`s without `Code`, while `streams.reduce` returns the original class node for one input. Cloche currently consumes the published `classpath-api-stubs` dependency for its common compilation classpath; this Spec does not prescribe a Cloche rollout or claim that a sibling checkout changes that dependency. ## Body preservation contract

`preserveMethodBodies` must be a task boolean input defaulting to `false`. With one input, the task must retain its current passthrough behavior, including existing `Code`, regardless of the option value. With multiple inputs and the option disabled, the current bodyless method intersection must remain unchanged. With multiple inputs and the option enabled, only methods surviving the existing member intersection are candidates for preservation. A candidate's `Code` must be retained only when all contributing inputs have `Code` and their bodies are structurally equal under the rules below. A missing method is handled by the existing member intersection, not by body comparison. Distinguish an absent `Code` attribute from a `Code` attribute with no executable instructions. `abstract` and `native` methods have no `Code` to preserve.

Structural equality is not semantic equivalence. For an already-common method identified by JVM name and descriptor:

1. Compare the complete ordered sequence of executable instructions, including unreachable instructions. Each opcode and its typed operands must agree: immediate values; local indexes and increments; type, field, and method owner/name/descriptor and interface flag; literal constants (including `Type`, `Handle`, and nested `ConstantDynamic` values); `invokedynamic` name/descriptor/bootstrap handle and ordered bootstrap arguments; array dimensions; and switch keys, bounds, and destinations. Compare constants by value and kind, not constant-pool indexes or object identity. An unknown instruction or constant kind does not establish equality.
2. Resolve branch and switch destinations to executable instruction positions, and compare those positions. Ignore ASM label identity, label names, redundant labels at the same position, and labels introduced solely for debug/frame data. A label at the end of the code maps to a distinct end sentinel. Thus different label layouts alone do not reject equal bodies, while a changed branch destination does.
3. Compare the complete **ordered** exception-handler table: start and end boundaries (end-exclusive), handler position, and caught type (including catch-all). Different ranges, priorities/order, handlers, or types do not establish equality. Do not omit this table just because the instruction streams match.
4. Ignore source line numbers, local-variable debug tables (including generic signatures), and stack-map frame contents and encoding when deciding this *instruction-and-handler* equality; this is not verifier equivalence. Different debug labels, debug tables, or frames alone must not change the preserve/omit decision. `max_stack`/`max_locals` are emitted from the chosen source, not treated as executable instruction operands. Code type annotations must be compared with their positions and values (including instruction, handler, and local-variable targets), or the affected `Code` must be treated as uncomparable. Any other Code metadata that cannot be compared reliably must likewise prevent preservation; supporting rare attributes is not required. Method-level annotations and declared exceptions remain owned by the existing intersection logic, not this comparator.

If a body qualifies, emit a complete `Code` body from one contributing method, with its own coherent labels, handlers, frames, debug information, and stack/local maxima; do not splice instructions and metadata from different inputs. Which input supplies the bytes is not a semantic guarantee. Comparing two bodies must be symmetric and the preserve/omit decision must be independent of input order. For three or more inputs, every contributing body must match the same structural rule; an intermediate bodyless intersection must not accidentally discard a previously valid all-input match or count as proof of equality. Byte-for-byte output and debug metadata need not be order-independent.

If any contributing `Code` is unequal, absent, or cannot be compared reliably, retain the already-common method declaration without `Code`. Do not synthesize a replacement body or fail solely because of that difference. `<init>` and `<clinit>` follow the same rule when they survive method intersection; constructor calls, initializer instructions, and handlers are not exempt. Identical constructors/initializers do not establish compatibility of their referenced superclass, fields, or helpers. No change to class, member, signature, or access intersection is required. Existing member intersection determines which declarations survive, including any mixed Code/no-Code access flags.

ASM exposes instruction lists, try/catch blocks, local variables, frame visits, max stack/locals, and instruction/type annotations separately; this is why comparing only opcodes or ASM node identities is insufficient. [ASM MethodNode API](https://asm.ow2.io/javadoc/org/objectweb/asm/tree/MethodNode.html) · [ASM MethodVisitor API](https://asm.ow2.io/javadoc/org/objectweb/asm/MethodVisitor.html)

## Input tracking and acceptance

When a task output retains or copies bodies, method-body changes in input artifacts whose contents can affect the stub output **must** invalidate the stub task's input state, so the task re-executes or obtains an output computed from the changed bodies; an unchanged selected output after reevaluation is allowed. A stale `UP-TO-DATE` or cached artifact is not. This includes any excluded artifact copied into the output if its changed bytes would change that copy. The option must participate in the task's input state. Currently `ResolvedArtifact.file` is annotated `@CompileClasspath` inside a `@CacheableTask`; Gradle documents that this normalization ignores method-body and static-initializer changes. This is a concrete cache correctness risk even without any compilation promise. Input tracking must cover body-bearing inputs when preservation is enabled and the one-input passthrough even when disabled. [Current annotations](../../src/main/kotlin/net/msrandom/stubs/GenerateStubApi.kt) · [Gradle input normalization](https://docs.gradle.org/current/userguide/incremental_build.html#sec:task_input_using_classpath_annotations)

Acceptance checks for the confirmed behavior:

- ASM reads the generated jar and observes `Code` for an eligible common method with two matching bodies; three matching inputs also retain it. Reordering inputs does not change the retain/omit decision. With one input, enabled and disabled runs both retain the existing body; with multiple inputs and the option disabled, the existing bodyless intersection remains.
- A changed opcode/operand, branch or switch target, bootstrap argument, or exception-handler range/type/order prevents a claim of equal bodies; unrelated line numbers, redundant labels, local-variable debug tables, or frame encoding alone do not. Compare Code type annotations by position and value or omit the body; unsupported Code metadata must not produce a false match. Unequal, absent, or uncomparable `Code` retains the common declaration without `Code`, without a substitute body or difference-only error. Include `<init>` and `<clinit>` fixtures and a non-Code `abstract`/`native` fixture.
- A body referring to a helper absent or different elsewhere is **not** used as proof of helper consistency; no load/run/compile/injection success test is a gate for body preservation.
- Gradle task checks change only the bytecode body of an included input jar between runs (no ABI change) and observe reevaluation and the selected output transition, both with up-to-date checks and build cache in scope. One-input passthrough must also invalidate on a body-only change with either option value. Toggling the option must change task input state.

## Scope and authority

This behavior applies only to `classpath-api-stubs`. Cloche activation, Codev changes, worker/coroutine changes, and unrelated historical refactoring are out of scope. No PRD or ADR for this feature was found in the owning repository when this Spec was drafted. The behavior above is confirmed; implementation design, Plan, Tasks, and completion are not established by this document.
